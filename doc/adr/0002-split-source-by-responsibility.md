# ADR 0002：按职责拆分单项目源代码

## 状态

已接受

## 日期

2026-07-22

## 背景

应用最初规模较小，入口、主窗体、仓库列表窗体、自绘控件、图标、模型和服务均位于 `TortoiseGitLauncher/Program.cs`。随着仓库管理功能完善，该文件增长到 1859 行。

已确认的“脚本执行”功能还会引入页面、配置模型、JSON 持久化、并发进程、输出缓冲和进程终止。如果继续集中在 `Program.cs`，修改冲突、职责耦合和回归风险都会明显增加。

## 决策

- 保持现有 WinForms 单项目、单可执行程序和 `TortoiseGitLauncher` 命名空间。
- `Program.cs` 只保留进程入口和顶层异常处理。
- 现有代码按 `UI`、`Models`、`Services` 拆分。
- `MainForm` 使用 partial class 将应用外壳与现有仓库管理页分开。
- 新增的大型独立功能优先放在 `Features/<FeatureName>/` 下，按功能纵向组织 UI、模型和服务。
- 本次拆分只移动原有类型和方法，不改变现有运行行为。

## 未采用的方案

### 继续维持单文件

短期修改简单，但脚本执行功能加入后会进一步扩大冲突和维护成本，不再适合当前规模。

### 立即拆分多个项目并引入依赖注入框架

当前应用仍是本地单进程工具，多个程序集和容器会增加构建、发布和理解成本，暂时没有足够收益。

### 全面重写仓库管理页

现有功能已经稳定，重写会扩大回归面。本次只做机械拆分，后续在真实需求驱动下逐步提取页面控件和服务。

## 影响

正面影响：

- 文件职责和功能落点更明确。
- 后续脚本功能可以独立开发，减少对仓库页面的影响。
- 模型、持久化和进程逻辑更容易进行针对性测试。

代价和约束：

- partial class 仍共享私有状态，只是组织边界，不是完整解耦。
- 新代码必须遵守依赖方向，不能因为访问方便而把业务逻辑重新放回主窗体。
- 文件移动后需要通过构建或等价检查确认隐式 `using` 和项目自动包含规则没有问题。
